# Use Case Specification: «Мастер Подземелий — Симулятор Битв»

## 1. Назначение системы

Программный симулятор массовых сражений для настольных ролевых игр (в первую очередь D&D 5e). Автоматизирует «бухгалтерию» боя — броски кубиков, учёт хитов, КД, дальностей, мультиатак и регенерации — и визуализирует его на клетчатой карте с токенами, чтобы ведущий (мастер) тратил время на историю, а не на подсчёты. Источник данных о монстрах — справочник **dnd.su** (оттуда парсятся статблоки).

## 2. Акторы

| Актор | Роль |
|---|---|
| **Мастер (пользователь)** | Настраивает стороны, запускает бой, наблюдает и вмешивается |
| **Симулятор (система)** | Проводит раунды, двигает токены, считает урон, пишет лог |
| **dnd.su (внешняя система)** | Веб-справочник, источник статблоков для импорта |
| **Файловая система** | Хранение JSON-настроек и выбранной темы |

## 3. Архитектурный обзор (модули)

Запуск: `python main.py` (нужен PyQt6). Интерфейс один — окно Qt в `qt_app.py`.

`MainWindow` держит карту в центре, слева тонкий тулбар, справа прячущуюся панель (участники, журнал, бестиарий). Настройка армий — отдельная страница, альянсы и редкие правила — диалог «Настройки боя». Подробности раскладки — в `docs/ui-redesign.md`. Расчёт живёт отдельно от виджетов: `battle_round` проводит раунд, `decision_engine` и `battle_strategies` выбирают цель и атаку, `combat_core` считает удары, `battle_map_model` держит сетку и BFS. Модели `Enemy`/`Attack` наследуют `Subject`: изменение состояния вызывает `notify()`, и список боя обновляет только «грязные» строки. Диалоги — `SideCreatorDialog` и `CreatureEditDialog` (`qt_editors.py`), импорт — `BestiaryDialog` (`qt_bestiary.py`) поверх `bestiary_core`. Тема — `qt_theme.py` (QSS, файл `battle_settings/theme.json`).

## 4. Use Cases

### UC-01. Переключение темы оформления
- **Актор:** Мастер.
- **Предусловие:** приложение запущено.
- **Основной поток:**
  1. Мастер кликает по квадратной кнопке внизу левого тулбара или выбирает «Вид → Переключить тему» (🌙 на тёмной / ☀️ на светлой).
  2. Система применяет палитру через QSS (`QtTheme`), перерисовывает векторные иконки и карту.
  3. Система сохраняет выбор в `battle_settings/theme.json`.
- **Постусловие:** интерфейс в новой теме; при следующем запуске тема восстанавливается.
- **Примечание:** тёмная — графитовая, светлая — тёплый «пергамент». Иконка темы — векторная кнопка фиксированного размера.

### UC-02. Призыв новой стороны (создание отряда)
- **Актор:** Мастер.
- **Предусловие:** открыта вкладка «Настройка армий»; на старте уже две карточки и круглая ➕-кнопка.
- **Основной поток:**
  1. Мастер кликает ➕. Система добавляет карточку со встроенным типом.
  2. Чтобы сменить состав, мастер жмёт кнопку на карточке. Система открывает диалог «Кого ведём в бой?».
  3. Мастер выбирает тактику отряда и путь: **импорт из бестиария** или **свои существа**.
  4. *Импорт:* система открывает `BestiaryDialog`; Мастер ищет монстра (поиск и загрузка статблока идут в **фоновом потоке**, окно не зависает), выбирает из списка, смотрит предпросмотр, жмёт «Импортировать». Система регистрирует тип в `EnemyFactory.CUSTOM_TYPES` (включая распарсенную **мультиатаку**) и возвращает имя в диалог.
  5. *Свои существа:* Мастер заполняет имя, хиты, КД, скорость, регенерацию, список атак (можно «Загрузить пресет» из встроенных типов — тогда **мультиатака пресета тоже переносится**), жмёт «Создать». Система регистрирует тип.
  6. Карточка показывает новый состав и тактику.
- **Альтернативный поток 4a:** Мастер закрыл окно импорта → диалог призыва остаётся открытым, ничего не потеряно.
- **Альтернативный поток 5a:** не введено имя или нет атак → система показывает предупреждение, состав карточки не меняет.
- **Постусловие:** карточка стороны существует с известным составом и тактикой; ➕ стоит в следующей свободной клетке сетки.

### UC-03. Настройка и удаление стороны
- **Актор:** Мастер.
- **Основной поток (настройка):**
  1. Имя стороны правится в поле на карточке.
  2. Тактика меняется комбобоксом прямо в карточке.
  3. Количество врагов — спинбоксом.
  4. Состав (импортный/кастомный тип) показан read-only; кнопка 🔄 переоткрывает окно призыва для смены состава той же стороны.
- **Основной поток (удаление):**
  1. Мастер кликает ✕ в углу карточки.
  2. Система спрашивает «Удалить отряд?» диалогом. Последнюю сторону удалить нельзя.
  3. «Да» → карточка и связанные данные убираются, сетка перестраивается (`relayout_cards`). «Нет» → карточка остаётся.
- **Постусловие:** сетка карточек отражает текущий набор сторон и подстраивает число колонок под ширину окна.

### UC-04. Сохранение и загрузка конфигурации
- **Актор:** Мастер (меню «Файл»: «Сохранить настройки» и «Загрузить настройки»).
- **Основной поток (сохранение):** система пишет JSON в `battle_settings/`, включая `num_sides`, имена/количества/типы/тактики сторон, **полные определения импортированных монстров** (`custom_types`) и настройки альянсов.
- **Основной поток (загрузка):** система восстанавливает `custom_types` в фабрику **до** создания сторон, сносит старые карточки и заново рождает каждую сторону через тот же путь, что и ➕ (`_create_new_side`), затем применяет альянсы/игнорирование.
- **Постусловие:** импортированные монстры переживают перезапуск программы; старые JSON-файлы совместимы (ключи не менялись).

### UC-05. Настройка альянсов
- **Актор:** Мастер (диалог «Настройки боя», секция «Альянсы», либо меню «Бой → Применить альянсы»).
- **Основной поток:** матрица галочек «кто кого игнорирует»; отмеченные стороны не атакуют друг друга.
- **Постусловие:** `ignore_sides` учитывается при выборе цели в бою и сохраняется в JSON.
- **Ограничение:** нумерация в матрице привязана к индексу стороны; удаление средней стороны после настройки альянсов сдвигает индексы (альянсы пересобираются при «Создать армии»).

### UC-06. Создание армий
- **Актор:** Мастер (кнопка «Создать армии»).
- **Основной поток:** система читает карточки, для каждой стороны создаёт `enemy_count` экземпляров через `EnemyFactory.create_enemy` (сначала проверяя `CUSTOM_TYPES`, затем встроенные типы), назначает стратегию по тактике, строит UI боя и альянсов, генерирует **резиновую карту** (`map_w`/`map_h` по числу сторон и макс. отряду), расставляет формации.
- **Исключение:** ошибка на любом шаге перехватывается и показывается диалогом.
- **Постусловие:** армии готовы, карта построена, токены расставлены.

### UC-07. Проведение раунда боя
- **Актор:** Мастер (кнопка «Провести раунд боя») или система в авто-режиме.
- **Предусловие:** армии созданы, есть живые бойцы.
- **Основной поток:**
  1. Система сбрасывает `moved_ft` всем и **синхронизирует `enemy.pos` с реальной сеткой карты** (единый источник истины — иначе цели выбираются по устаревшим координатам).
  2. Для каждого живого воина по сторонам:
     - **Выбор цели** (`_pick_target`, трёхуровневый): ① враг в радиусе оружия → бей на месте; ② враг в радиусе «оружие + скорость» → подойди и ударь; ③ никого вокруг → беги к **ближайшему** (а не к «идеальному» через всю карту). Критерий «лучший» внутри уровня — по стратегии (слабейший/опаснейший/случайный/раненый союзник).
     - **Развёртка ударов** (`_resolve_strikes`): если есть `multiattack` — плоский список по `count` (имена матчатся по `Attack.name`, нераспознанные тихо выпадают); иначе — одна атака по стратегии.
     - **Движение** (`move_towards`): BFS в обход союзников до клетки, откуда `reach = min(range ударов)`; если путь намертво заблокирован — случайный «дрейф»-шаг (анти-пробка). Галочка «Автоперемещение» обязательна для подхода.
     - **Выполнение ударов** (`execute_strikes`): каждый удар — бросок через чистый `Enemy.perform_attack` (d20+бонус vs КД, крит с удвоением, тип урона). **Цепное добивание:** если цель погибла или удар её не достаёт, оставшиеся удары перенаправляются на ближайшего живого врага в радиусе *этой* атаки с текущей позиции (`_nearest_in_range`); если такого нет — удар честно пропадает.
  3. Фаза регенерации (монстры с `regen`).
  4. Проверка исхода (≤1 живая сторона → победа/ничья).
  5. События пишутся в структурированный журнал; список существ обновляется в конце раунда (observer-«грязные» строки).
- **Альтернативный поток:** без карты (нет позиций) дистанции = 0 → все атаки достают, поведение деградирует к «бей по критерию стратегии» без регрессий.
- **Постусловие:** раунд проведён, лог пополнен, реген зафиксирован.

### UC-08. Работа с картой боя
- **Актор:** Мастер (карта — основная сцена окна; «Вид → Карта боя»).
- **Основной поток (выделение/перемещение):**
  1. Клик по токену выбирает его (координаты сцены `QGraphicsView`: прокрутка и зум не сбивают попадание).
  2. Зелёной зоной подсвечивается всё, куда токен дойдёт за ход с учётом `speed − moved_ft`.
  3. Клик по свободной клетке в зоне перемещает токен и списывает футы; вне зоны — сообщение «не хватает скорости».
- **Постусловие:** позиции на карте и `enemy.pos` согласованы (см. UC-07, шаг 1).

### UC-09. Наблюдение за боем
- **Актор:** Мастер.
- **Основной поток:** журнал боя (попадания/промахи/криты/смерти/реген, с указанием имени атаки и «vs AC»); список воинов с живыми мёртвыми; кнопки «Массовое редактирование» и «Показать статус».
- **Постусловие:** мастер видит состояние без ручных подсчётов.

### UC-10. Импорт монстра из бестиария (детализация UC-02)
- **Актор:** Мастер + dnd.su.
- **Основной поток:** запрос поиска → разбор ссылок бестиария в `bestiary_core` (фильтр «запрос в имени») → клик по результату → загрузка страницы → `parse_statblock` (имя, хиты, КД, скорость, реген, атаки, дальности) → разбор мультиатаки → предпросмотр → регистрация.
- **Исключение:** сеть или разбор упали → сообщение в главном потоке; окно не зависает, потому что `requests` идёт в фоновом потоке (`qt_async`).
- **Ограничение:** условные замены атак («если цель далеко — вместо меча лук») в мультиатаку **не** тащатся сознательно (extension point заложен).

## 5. Нефункциональные требования

| Категория | Требование / реализация |
|---|---|
| **Производительность** | сотни юнитов: observer-«грязные» строки вместо полной перерисовки, BFS ограничен глубиной скорости, список существ обновляется в конце раунда |
| **Отзывчивость UI** | сетка карточек под ширину окна; карта на `QGraphicsView` (зум колесом, панорама) |
| **Устойчивость к блокировкам** | сеть и пакетная симуляция в фоновых потоках (`qt_async`), виджеты остаются на главном потоке |
| **Консистентность данных** | единый источник истины о позиции (`pos` ↔ сетка карты, синхронизация на входе раунда); `to_dict`/`from_dict` симметричны (включая `multiattack`, `pos`) |
| **Совместимость** | старые JSON открываются; бой без карты деградирует безопасно |
| **UX** | карта в центре, иконки тулбара, боковая панель с вкладками, редкие настройки в диалоге; видимость панелей помнит `QSettings` |

## 6. Границы и бэклог

1. **Координация толп** — сейчас каждый воин думает сам; «концентрация огня» и обходы с флангов не гарантированы. Следующий эшелон: **flow fields** (волновое поле на отряд) вместо по-воинного BFS.
2. **Условные способности** — замена атаки по условию и прочие «если…» не моделируются (только фиксированные мультиатаки).
3. **Труднопроходимая местность / летуны** — BFS пока по единой стоимости клетки.
4. **Регистрация пользователей и SQL** — шаблоны живут в JSON; для личной библиотеки и масштаба planned пользовательские аккаунты + БД.
5. **Красота интерфейса** — функционально всё на месте, но визуальный полиш (анимации, тени, иконки атак) — отдельный трек.
